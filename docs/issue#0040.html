Issue #40 — rdmanet: 批量收发 API — 2026-06-13

Design Decisions

Decision Batch = same framing under one lock, not a new wire format

Ambiguity: "摊薄每次 post/poll 的固定开销" — how much of the cost to amortize.

Choice: SendBatch holds sendMu once for the whole batch and reuses sendFrame per message; RecvBatch blocks for the first message then drains already-reassembled messages non-blockingly via tryNextMessage. No new frame type.

Rationale: The dominant amortizable cost is lock acquisition and the recv-side blocking wait; reusing the existing framing keeps batch and single-message semantics identical (criterion: "可混用，语义一致").

Decision RecvBatch returns 1..max (never zero, never blocks for the full max)

Ambiguity: "一次最多收割 max 条…至少返回 1 条（无消息则阻塞）".

Choice: Block for message 1, then opportunistically collect up to max−1 more that are already available, stopping as soon as none is ready.

Rationale: Exactly the spec's contract; avoids latency from waiting to fill a batch that may never fill.

Deviations

Deviation None

Implementation followed the spec. Both Conn (SendBatch/RecvBatch) and PacketConn (WriteToBatch/ReadFromBatch) batch APIs are provided as the criterion requested.

Tradeoffs

Tradeoff Synchronous per-frame send within the batch vs. pipelined posts

Alternatives: (a) reuse sendFrame (one in-flight frame, wait per frame); (b) post all frames of the batch then drain all completions.

Pros/cons: (a) reuses proven, credit-gated code and keeps correctness obvious; the lock amortization is still won. (b) higher throughput but needs a redesigned slot/credit/completion accounting and risks reordering bugs.

Chosen: (a) — capture the lock-amortization win now with zero new concurrency risk; true pipelining can be a later perf pass once the bench tool (#44) quantifies the gap.

Tradeoff PacketConn batch reuses WriteTo/ReadFrom rather than a bespoke path

Alternatives: chained ibv_post_send wr-list vs. looping the single-datagram path.

Pros/cons: wr-list is the real verbs batching primitive (max throughput); looping is trivial and correct but only amortizes Go-side overhead.

Chosen: looping for v1 (UD send path is single-slot/serialized anyway); a wr-list fast path is a clean future optimization behind the same API.

Open Questions
