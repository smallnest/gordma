Implementation Notes

Issue #37 — rdmanet: 流式 Read/Write 适配层 — 2026-06-13

Design Decisions

Decision Read buffers the leftover of an oversized message

Ambiguity: "Read 可跨消息边界连续取字节" — behavior when a message is larger than the caller's slice was unspecified.

Choice: A streamReader holds the unread tail of the last message; each Read drains the buffer first, fetching the next message via recvMsg only when empty. So reading N bytes at a time across M messages reconstructs the exact concatenated byte stream.

Rationale: This is the standard stream-over-datagram adapter; it gives faithful io.Reader semantics (≥1 byte per Read unless EOF/empty dst).

Decision Write = exactly one SendMsg

Ambiguity: Whether Write should chunk or coalesce.

Choice: Each Write sends the whole slice as one message and returns len(p), nil on success (io.Writer's full-write contract). Fragmentation for large p is handled transparently below by #36.

Rationale: Simplest correct mapping; the message layer already fragments, so Write need not.

Decision Adapter logic extracted to a build-agnostic streamReader

Ambiguity: "单元测试覆盖流式语义（含跨消息读取）" needs hardware-free testability.

Choice: The buffering logic lives in stream.go (no cgo) parameterized by a recv func() ([]byte, error); Conn.Read wires it to the real transport. Tests feed canned message sequences.

Rationale: Lets the cross-message semantics be unit-tested (and raced) without an RDMA device.

Deviations

Deviation None

Implementation followed the spec as written. The var _ io.ReadWriteCloser = (*Conn)(nil) assertion was already added in #32 and continues to hold.

Tradeoffs

Tradeoff Mixing Read with RecvMsg: documented constraint, not enforced

Alternatives: (a) document that Read and RecvMsg must not be mixed on one Conn; (b) actively forbid it with a mode flag/error.

Pros/cons: (a) zero overhead, trusts the caller; (b) safer but adds state and a runtime error to a hot path.

Chosen: (a) — documented on both Read and the package. The hazard (Read buffering part of a message RecvMsg won't see) is clearly stated; enforcing it would complicate the API for an unusual misuse.

Open Questions

Question Should mixing Read/RecvMsg be hard-enforced later?

Assumption: Documentation suffices for v1.

Verify: If real misuse appears, add a one-shot "receive style" latch that errors on the second style. Cheap to add without breaking the API.
