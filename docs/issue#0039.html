Implementation Notes

Issue #39 — rdmanet: UD PacketConn 与 Addr 格式 — 2026-06-13

Design Decisions

Decision GRH handling: recv slots carry +40 bytes, payload skips it

Ambiguity: UD prepends a 40-byte Global Routing Header to every received datagram; the spec doesn't mention it.

Choice: Recv slots are sized mtu + GRHLength; ReadFrom skips the leading GRHLength bytes and reports ByteLen - GRHLength as the payload length. Send slots are plain mtu.

Rationale: This is mandatory for UD correctness; getting it wrong corrupts every received datagram.

Decision Per-destination AddressHandle cache keyed by Addr.String()

Ambiguity: "内部管理 AH 缓存（按目的地址复用）".

Choice: A map[string]*AddressHandle keyed on to.String(), populated lazily in ah() under a mutex; all cached AHs are closed in Close.

Rationale: Addr.String() (gid%qpn[#qkey]) is a stable, complete key; creating an AH per datagram would be wasteful.

Decision Single send slot + serialized writers; busy-poll completions

Ambiguity: Concurrency and completion model for UD weren't specified.

Choice: WriteTo serializes on sendMu and uses slot 0, waiting for its send completion; ReadFrom serializes on recvMu and busy-polls. One reader + one writer are safe.

Rationale: Keeps the first UD cut simple and correct; event-mode polling arrives in #43, batch send in #40.

Deviations

Deviation ReadFrom's returned Addr carries only SrcQP (+ default QKey)

Spec: ReadFrom reports "the sender's address".

Implemented: The returned *Addr has QPN = completion's SrcQP and QKey = DefaultQKey; the sender's GID is not parsed out of the GRH.

Why: SrcQP comes directly from the work completion and is enough to distinguish/return-to senders that registered via the out-of-band path (#42). Parsing the GID from the GRH is extra cgo work of limited value for v1; can be added if needed.

Tradeoffs

Tradeoff Fixed QKey (DefaultQKey) vs. per-endpoint QKey

Alternatives: (a) all endpoints share DefaultQKey; (b) configurable QKey per PacketConn.

Pros/cons: (a) simplest — any two rdmanet UD endpoints interoperate out of the box; (b) supports QKey-based isolation but adds an option and handshake field.

Chosen: (a) for v1; Addr already carries a QKey field (and String/ResolveAddr round-trip it), so per-endpoint QKey can be layered on without an API break.

Open Questions

Question Recover sender GID from GRH?

Assumption: SrcQP-only return Addr is sufficient for v1 (combined with #42's registry, peers are known by name/Addr).

Verify: If a use case needs to reply to an unknown sender purely from ReadFrom, parse the GRH's sgid; the GRH bytes are already in the recv slot.
