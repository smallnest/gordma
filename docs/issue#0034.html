Issue #34 — rdmanet: TCP 握手方式建连 — 2026-06-13

Design Decisions

Decision Reuse the verbs setup sequence from perftest.SetupTCP

Ambiguity: "走 handshake 包交换…内部完成 INIT→RTR→RTS" — the order and resource ownership were left to the implementer.

Choice: buildHandshakeConn opens the device, allocates PD/CQ, creates the RC QP, registers a bounce MR, then exchanges handshake.EndpointInfo and drives INIT→RTR→RTS — mirroring the proven perftest.SetupTCP flow, but owning the resources on the rdmanet Conn.

Rationale: The perftest path is the reference implementation of this exact handshake; following it minimizes the chance of a subtle MTU/PSN/GID mistake.

Decision Same Conn type for both build paths; ownership flag is cm != nil

Ambiguity: "两种建连方式返回的 Conn 行为一致".

Choice: One Conn struct. rdma_cm fills cm (which owns PD/CQ/QP); handshake fills ctx/pd/cq/qp/mr directly. Close branches on cm != nil and otherwise releases MR→QP→CQ→PD→Context in order.

Rationale: Callers stay agnostic; only Close needs to know which path built it.

Deviations

Deviation Handshake Listen succeeds without an RDMA device

Spec: Implies a working connection establishment.

Implemented: Listen(...WithHandshake()) only opens a TCP listener; verbs resources are built lazily in Accept. So Listen succeeds even with no NIC, and the device requirement surfaces on Accept.

Why: Matches handshake.Server's pure-TCP nature and lets the unit test (and CI) verify the listener path without hardware.

Tradeoffs

Tradeoff Bounce MR registered at connect time vs. lazily

Alternatives: (a) register the bounce MR during handshake setup; (b) defer MR registration to the first SendMsg/RecvMsg (#35).

Pros/cons: (a) the local RKey/addr can be carried in the handshake (enabling one-sided ops later) and the Conn is fully armed on return; (b) leaner if a Conn never sends, but the handshake would lack RKey/addr.

Chosen: (a) — the handshake EndpointInfo already has RKey/RemoteAddr fields; populating them now keeps the wire contract complete and is what perftest does.
