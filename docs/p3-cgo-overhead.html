为何慢于原生 RDMA（CGO 开销）

同一张网卡、同样的 verbs 调用序列，gordma 跑出来的吞吐就是比 C 写的 perftest 低一截。这不是 bug，而是 Go 经由 cgo 调用 libibverbs 的固有代价。 这一节把这笔开销拆开，告诉你它有多大、出在哪、以及怎么把它摊薄到可接受。

先看实测差距

某台 400G RoCE v2 主机，64KB 消息、-n 1000000，三个 Send/Recv 带宽工具换算到同一单位后：

工具语言/路径吞吐消息率
ib_send_bwC（原生 verbs）~392 Gb/s0.747 Mpps
go_send_bwGo + cgo（perftest 包）~314 Gb/s0.598 Mpps
go_rdmanet_bw --rawGo + cgo（RawConn）~216 Gb/s0.413 Mpps
先对齐单位 这三个数字原始输出单位各不相同，差出 8 倍：ib_send_bw 是 MiB/s（2²⁰）、 go_send_bw 是 MB/s（10⁶）、--raw 是 Gb/s（10⁹ bit）。直接比原始数会得出完全错误的结论。 详见 go_rdmanet_bw 详解。

注意三者比值在吞吐和消息率上完全一致（0.747 : 0.598 : 0.413），说明差距是纯粹的 每个工作请求（WR）的固定开销，与数据量无关——这正是 cgo 的典型特征。

一次 cgo 调用到底贵在哪

很多人以为 cgo 慢是因为「调用 C 函数本身慢」。其实不是。一次 C.ibv_post_send(...) 现代 Go 上约 40–60ns，开销主要不在那句 C 调用，而在它前后运行时要做的协调：

环节做了什么能不能省
栈切换从 goroutine 的小栈切到系统栈（g0），因为 C 代码需要一个完整的、不会被移动的 C 栈不能——只要从 Go 进 C 就得做
调度器协调标记当前 P「进入了 syscall/C」，让调度器和抢占式 GC 知道别去抢占、别移动这个 goroutine 的栈不能
参数编组把 Go 的参数按 C ABI 摆好；cgo 在编译期生成静态 wrapper，这步几乎零成本已是最优
指针检查cgo 在调用边界检查传入指针是否违反「Go 指针不能指向含 Go 指针的内存」规则可减少（见下）

关键在于前两项与你调用的是哪个 C 函数无关，是一道过不去的「进出栅栏」。原生 C 程序直接 call 进 libibverbs，没有这道栅栏，所以同样的 verbs 序列就是更快。

为什么影响的是「消息率」而不是「带宽」

RDMA 数据搬运本身是网卡 DMA 完成的，CPU 不碰数据——所以 cgo 开销不按字节计，而是 按工作请求计。把上面的吞吐换算成每个 WR 的耗时：

go_send_bw : 1e6 WR / ~1.67s  ≈ 1.67 µs/WR
RawConn    : 1e6 WR / ~2.42s  ≈ 2.42 µs/WR

大包（64KB）下每个 WR 搬运很多字节，固定开销被稀释，带宽差距还能容忍； 小包高频时每个 WR 搬的字节少，固定开销占比飙升，消息率（Mpps）差距会被放大到刺眼。 所以 cgo 开销的真正战场是小消息、高 PPS 的场景。

gordma 怎么把它摊薄

既然每次穿越 cgo 边界都要交「过路费」，优化思路就一条：减少穿越次数。

  • 批量提交（PostSendBatch / PipelineBatch）：用 C 侧 WR 链表把 N 个工作请求 一次 ibv_post_send 提交，把过路费从「每 WR 一次」降到「每批一次」。小包消息率因此可提升约一个数量级。
  • 忙轮询（PollBusy）：避免事件驱动每次唤醒都要 ibv_get_cq_event + 一次系统调用； 忙轮询直接读 CQ 内存，热路径上几乎不过 cgo 边界。
  • 复用 scratch 缓冲：PostSend 热路径用每 QP 预分配的 C 侧 SGE 数组， 避免每次调用都做指针检查和堆分配。
  • 预注册内存 + 零拷贝（SendBuffer）：省掉 bounce buffer 拷贝（这部分是 CPU 成本，不是 cgo 成本，但同样压低 per-WR 开销）。
还有一层差距 上表里 go_send_bw（314）和 RawConn（216）都是 Go + 每 WR 一次 cgo， 却仍差约 1.45 倍。这部分不是 cgo 能解释的，是库实现里尚待优化的空间（用 GORDMA_PROBE=1 看 post/poll 占比可定位）。换句话说：cgo 解释了 Go 追不上 C 的那部分， 但追平 go_send_bw 是另一回事。

能不能换掉 cgo？libffi 行不行

不行，libffi 只会更慢。它在运行时读类型描述符、动态拼调用栈帧（本质是反射式调用）， 比 cgo 编译期生成的静态 wrapper 更慢；而且上面那道「栈切换 + 调度器协调」的栅栏它一样省不掉。 libffi/purego 那类方案的价值是免 C 工具链、纯 Go 交叉编译，不是性能。

真要逼近原生 C，只有两条路，代价都不小：

方向思路代价
循环下沉到 C一次 cgo 调用驱动「post 满 → poll → 补发」整个流水线循环，每秒只过界几次而非几十万次失去 Go 侧对每个 WR 的控制，灵活性下降
Direct Verbs / DevX在 mmap 的内存里直接构造 WQE、敲 doorbell（mmio 写），全程在 Go 里完成，每个 WR 零 C 调用实现复杂，且绑定特定网卡（如 mlx5）

该不该在意

  • 大多数业务：gordma 即便有 cgo 开销，吞吐仍是 TCP 的数十倍、延迟低一个数量级。这点开销完全不该是你的瓶颈。
  • 大包传输：固定开销被字节数稀释，gordma 和原生差距很小，放心用。
  • 小包、极致 PPS、要榨干网卡：先上 RawConn + 批量 + 忙轮询； 若仍不够，才考虑上面两条「下沉」方案，或直接用 C 的 perftest 做基准。
一句话 cgo 是 Go 调用 RDMA 必交的过路费，按工作请求计、不按字节计；用批量和忙轮询把穿越次数压下去， 它就不再是瓶颈。想看它在你的负载上到底占多少，跑 GORDMA_PROBE=1 go_rdmanet_bw --raw 看 post/poll 拆分。
