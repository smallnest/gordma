Issue #35 — rdmanet: RC 消息语义 SendMsg/RecvMsg — 2026-06-13

Design Decisions

Decision One SEND = one message; WRID carries the slot index

Ambiguity: "保留消息边界" without specifying the framing.

Choice: Each SendMsg copies the payload into one bounce-buffer slot and posts one signaled SEND; each recv slot is a separate WR. The completion's ByteLen gives the message length, and the WRID identifies which slot filled — so boundaries are intrinsic to the SEND/RECV pairing, no length header needed yet.

Rationale: RC SEND is message-oriented; one-WR-per-message is the simplest boundary-preserving scheme. Length-prefixed framing only becomes necessary for fragmentation (#36).

Decision Single background poller + channels for sync

Ambiguity: "一个 goroutine 收 + 一个 goroutine 发安全" — the concurrency mechanism was open.

Choice: One poller goroutine drains the CQ and dispatches: SEND completions → sendDone channel, RECV completions → recvQ channel. sendMsg/recvMsg block on those channels. Senders serialize on sendMu, receivers on recvMu.

Rationale: A single CQ consumer avoids races on ibv_poll_cq; channels give clean blocking semantics and Close-wakeup via the closed channel.

Decision Transport built lazily on first SendMsg/RecvMsg

Ambiguity: When to register the bounce rings.

Choice: sync.Once in Conn.transport(); a Conn used only for establishment never registers rings or starts a poller.

Rationale: Keeps establishment cheap and makes the data path independent of which build path (cm vs handshake) produced the QP — dataPath() abstracts that.

Deviations

Deviation Large-message fragmentation deferred to #36

Spec: US-004 mentions "内部维护预注册的环形 bounce buffer"; the PRD's large-message split is a separate criterion.

Implemented: A message larger than one slot returns ErrMessageTooLarge. The PRD explicitly splits flow-control + fragmentation into #36 (US-004 后半), so this Issue stops at single-slot messages.

Why: Matches the agreed Issue decomposition; #36 layers credit flow-control and fragmentation on this ring.

Tradeoffs

Tradeoff RecvMsg allocates vs. RecvMsgBuf zero-alloc

Alternatives: only-allocating API, only-caller-buffer API, or both.

Pros/cons: RecvMsg (alloc) is ergonomic; RecvMsgBuf (caller buffer) avoids a per-message allocation but must handle the too-small case.

Chosen: both, as the Issue lists both. RecvMsgBuf returns ErrShortBuffer (boundary preserved, slot still reposted) rather than truncating.

Tradeoff Busy-poll loop with Gosched in this Issue

Alternatives: busy-poll now vs. wait for the CompChannel event mode (#43).

Pros/cons: busy-poll is simplest and unblocks #35/#36/#37 testing; it burns a core. Event mode is the CPU-friendly default but is scheduled for #43.

Chosen: busy-poll with runtime.Gosched() on empty polls; #43 introduces WithPollMode and the event path sharing this same dispatch logic.
