Design Decisions

Decision API surface declared once, structs split per build

Ambiguity: The Issue requires identical exported API across the cgo (real) and stub builds, mirroring the root package's *_linux.go/*_stub.go pattern, but does not say how to avoid duplicate type declarations.

Choice: Conn/Listener/PacketConn structs and their methods live in conn_linux.go and conn_stub.go (build-tagged); shared, build-agnostic code (Options, config, Addr, the io.ReadWriteCloser assertion) lives in untagged files.

Rationale: Matches the established root-package convention so contributors see one familiar layout; keeps option/addr logic testable on any platform without cgo.

Decision Addr.String() format and QKey omission rule

Ambiguity: PRD fixes the gid%qpn[#qkey] shape and says "QKey non-default appended", but does not define numeric base or what counts as "default".

Choice: QPN/QKey rendered hex with 0x prefix; QKey omitted when it equals 0 or DefaultQKey (0x11111111). ResolveAddr accepts both hex (0x) and decimal for forgiving parsing.

Rationale: Hex matches how QPNs are shown in verbs tooling; treating both 0 and the well-known default as "omit" keeps round-trips stable since an un-set QKey parses back to 0.

Decision Default PollMode = PollEvent

Ambiguity: US-011/PRD says the default "should be documented" and suggests PollEvent, without mandating it.

Choice: PollEvent is the zero value (iota 0) and the documented default.

Rationale: Event-driven draining is the CPU-friendly choice for a general-purpose default; busy-poll is opt-in for latency-sensitive users.

Deviations

Deviation Linux build returns an internal not-implemented error, not ErrNotSupported

Spec: The Issue's stub criterion says entry points return gordma.ErrNotSupported; it does not prescribe the cgo build's behavior for the skeleton.

Implemented: The cgo build's entry points return an unexported errNotImplemented sentinel until later issues (#33+) wire up real RDMA.

Why: On Linux+cgo the platform is supported, so returning ErrNotSupported would be misleading. The skeleton's job is the package/option/API scaffold; returning a distinct "not implemented yet" error is honest and gets replaced as each feature lands.

Tradeoffs

Tradeoff Custom GID parser vs. reusing root package

Alternatives: (a) add an exported ParseGID to the root gordma package and call it; (b) parse the colon-separated GID form locally in rdmanet.

Pros/cons: (a) avoids duplication but expands the root package's API surface and touches files outside this Issue's scope; (b) keeps the change contained to rdmanet/ at the cost of a small local parser mirroring GID.String()'s 8-group format.

Chosen: (b) — FR-16 forbids modifying the root package's API; a 15-line local parser is the right ownership boundary for the skeleton.
