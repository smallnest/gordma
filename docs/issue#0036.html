Implementation Notes

Issue #36 — rdmanet: credit 流控与大消息分片重组 — 2026-06-13

Design Decisions

Decision 8-byte per-frame header carries length + flags

Ambiguity: The spec requires fragmentation/reassembly and credit flow control but not the wire format.

Choice: Every SEND now carries a fixed frameHeaderSize (8-byte) header: 1 flags byte (flagMore, flagCredit), 3 reserved, 4-byte big-endian value (payload length for DATA, credit count for CREDIT). Usable payload per frame = slotSize - frameHeaderSize.

Rationale: A tiny header is enough to express both message boundaries (flagMore) and in-band credit returns, avoiding a second channel.

Decision Credit = counting semaphore seeded to peer recv depth

Ambiguity: "基于信用的流控" without a specific scheme.

Choice: A creditTracker (mutex+cond semaphore) seeded with depth. Sender acquire()s one credit per frame and blocks at zero; the receiver returns credits via in-band flagCredit frames as it consumes recv slots. Frames are never posted faster than the peer can receive, so RNR cannot occur.

Rationale: Classic credit/window flow control; the cond-var semaphore is simple and Close-aware.

Decision Build-agnostic framing/credit/reassembly in non-cgo files

Ambiguity: "go test -race 通过（stub + 模拟路径）" implies hardware-free testability.

Choice: framing.go, credit.go (no build tag) hold the header codec, reassembler, fragment math, and credit semaphore — all unit-tested under -race with no device. Only the verbs glue (transport_linux.go) is cgo-tagged.

Rationale: Maximizes the surface verifiable in CI without RDMA hardware, satisfying the race-test criterion.

Deviations

Deviation ErrMessageTooLarge now means "exceeds reassembly cap", not "exceeds one slot"

Spec (#35): ErrMessageTooLarge was returned for a message larger than one bounce slot.

Implemented: With fragmentation a message spans many frames, so the guard moved to a 64 MiB maxMessageBytes cap (and a matching receive-side ErrMessageTooLargeReassembly).

Why: Single-slot was a #35 placeholder; #36's whole point is removing it. The cap now protects the receiver from unbounded reassembly rather than capping legitimate large sends.

Tradeoffs

Tradeoff Dedicated credit send slots vs. reusing data slots

Alternatives: (a) reserve a few extra send slots exclusively for credit frames; (b) send credit frames through the normal data-slot pool.

Pros/cons: (a) credit returns never contend with data sends or consume flow-control credits (deadlock-safe); (b) simpler bookkeeping but a full send ring could stall credit returns, risking deadlock.

Chosen: (a) — 4 reserved credit slots with a separate WRID space (creditWRIDBase). Credit frames are small and must always make progress to avoid a credit/send deadlock.

Tradeoff Synchronous per-frame send vs. pipelined

Alternatives: wait for each frame's completion before the next, vs. post all frames then drain completions.

Pros/cons: synchronous is simple and bounds in-flight frames to 1 (plus credit gating); pipelined is faster but needs careful slot/credit accounting.

Chosen: synchronous for correctness now; credit gating already bounds the peer-side ring. Pipelining is a later optimization (batch API #40 will push throughput).

Assumption: Returning one credit per consumed frame is correct but chatty; batching credit returns (e.g. return N when N/2 slots freed) would cut control traffic.
