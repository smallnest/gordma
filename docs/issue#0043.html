Implementation Notes

Issue #43 — rdmanet: CQ poller 双模式 — 2026-06-13

Design Decisions

Decision Shared dispatch, two drain strategies

Ambiguity: "两种模式下功能行为一致…共享同一套完成分发逻辑".

Choice: Extracted dispatch(wc) (routes one completion) and drainOnce(wc) (poll + dispatch a batch). PollBusy spins on drainOnce yielding on empty; PollEvent arms via ReqNotify, drains, then blocks on WaitEvent. Identical dispatch in both.

Rationale: Guarantees behavioral equivalence by construction — only the wake strategy differs, the completion handling is one code path.

Decision Event mode binds a CompChannel to the CQ at creation

Ambiguity: A CQ can only deliver events if created with a completion channel.

Choice: For PollEvent, handshake Conn and PacketConn create a CompChannel and pass it to CreateCQ; the channel is closed in Close. PollBusy uses a plain CQ.

Rationale: The channel must exist before the CQ; deciding by pollMode at setup keeps busy-mode allocation-free.

Decision Arm-before-drain ordering

Ambiguity: Event-mode races: a completion landing between drain and re-arm could be missed.

Choice: ReqNotify (arm) → drainOnce → (if empty) WaitEvent. Arming before draining means any completion after the drain still triggers the already-armed notification.

Rationale: Standard libibverbs event-loop discipline to avoid lost wakeups.

Deviations

Deviation rdma_cm Conn silently falls back to busy-poll

Spec: WithPollMode applies to Conn and PacketConn.

Implemented: The rdma_cm path's CQ (created by the root CMConn) has no completion channel. If event mode is requested there, the poller detects ErrNoChannel on ReqNotify/WaitEvent and permanently downgrades to busy-poll rather than erroring.

Why: rdmanet must not modify the root package (FR-16) to bind a channel to the CM-created CQ. The handshake path (which rdmanet owns) honors event mode fully; the CM path degrades gracefully instead of failing. Functionally identical, only the CPU profile differs.

Tradeoffs

Tradeoff Default PollEvent vs. PollBusy

Alternatives: default to lowest-latency (busy) or lowest-CPU (event).

Pros/cons: busy gives best latency but pins a core per connection; event is friendly to many-connection servers at a small latency cost.

Chosen: PollEvent default (per the issue's recommendation) — a general-purpose library should not burn a core by default; latency-sensitive users opt into PollBusy.

Open Questions

Assumption: Busy-poll fallback for CM-built Conns is acceptable.

Verify: If event mode on the CM path is wanted, the root package would need to optionally create its CQ with a completion channel — a small root-package enhancement for a follow-up issue.
