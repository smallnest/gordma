Implementation Notes

Issue #44 — rdmanet: 基准工具 go_rdmanet_bw / go_rdmanet_lat — 2026-06-13

Design Decisions

Decision Standalone flag parsing, not perftest.ParseArgs

Ambiguity: "与现有 cmd 一致的常用 flag" — reuse perftest's parser or roll new flags?

Choice: The two tools use their own flag.FlagSet with the familiar letters (-d/-i/-x/-s/-n/-p) plus rdmanet-specific -handshake and -poll=busy|event.

Rationale: perftest.Config is tailored to the low-level tools (RC/UD transport, tx-depth, rdma_cm -R); rdmanet's option set is different enough that a small dedicated parser is clearer than bending the perftest one. Flag letters stay consistent for muscle memory.

Decision bw = one-way send flood; lat = ping-pong

Ambiguity: How to measure bandwidth vs latency over a message API.

Choice: go_rdmanet_bw client sends N messages as fast as credits allow and reports Gb/s; go_rdmanet_lat does N send→echo round trips and reports avg/p50/p99/min/max.

Rationale: Mirrors the intent of perftest's *_bw/*_lat split using the high-level SendMsg/RecvMsg surface.

Deviations

Deviation No throughput comparison number baked in

Spec: "验证性能开销相对原始 verbs 路径可接受".

Implemented: The tools emit Gb/s and latency percentiles, but no automated comparison against go_send_bw is included.

Why: A meaningful comparison requires running both tool families on real RDMA hardware, which isn't available in this build/CI environment. The tools are the instrument; the measurement is an operator step (documented in their help/output).

Tradeoffs

Tradeoff New cmd tools vs. extending perftest

Alternatives: add an rdmanet mode to the existing six tools, or add two new ones.

Pros/cons: extending risks touching/breaking the existing tools (forbidden by the issue); new tools are isolated and leave the originals untouched.

Chosen: two new tools — the issue explicitly requires the existing six be left unchanged.
