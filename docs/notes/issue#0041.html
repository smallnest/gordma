Implementation Notes

Issue #41 — rdmanet: 零拷贝 Buffer 借还接口 — 2026-06-13

Design Decisions

Decision Two-SGE send: header from bounce slot, payload from user MR

Ambiguity: "零拷贝收发" — how to keep the frame header while avoiding the payload copy.

Choice: sendBuffer posts a SEND with two SGEs: the 8-byte frame header lives in a reserved credit slot, and the payload SGE points directly at the user's registered Buffer MR. The NIC gathers both, so the payload is DMA'd straight from caller memory — no bounce copy.

Rationale: Scatter/gather is exactly how verbs avoids copies; the header still rides the same framing the receiver already understands.

Decision Atomic lifecycle state machine (idle/inFlight/released)

Ambiguity: "借还状态机与误用（如重复释放）".

Choice: A build-agnostic bufferState using atomic.Int32: beginSend (idle→inFlight) rejects concurrent/duplicate sends with ErrBufferInFlight and use-after-close with ErrBufferReleased; release is one-shot (double-release → ErrBufferReleased).

Rationale: Atomic CAS keeps the hot send path lock-free w.r.t. the buffer and makes the misuse cases precise and -race-testable without hardware.

Decision Distinct WRID space for buffer-send completions

Ambiguity: How the poller distinguishes zero-copy sends from data/credit sends.

Choice: Added bufferWRIDBase = 1<<48 above the existing data (<1<<32) and credit (<1<<48) WRID ranges; the poller routes buffer-send completions to a dedicated bufDone channel.

Rationale: Reuses the established WRID-partitioning convention from #36; no ambiguity in the completion handler.

Deviations

Deviation RecvBuffer currently copies (not yet true zero-copy on recv)

Spec: "Conn.SendBuffer / Conn.RecvBuffer（或等价借还模型）零拷贝收发".

Implemented: SendBuffer is genuinely zero-copy. RecvBuffer reassembles via the existing bounce ring then copies into a freshly registered Buffer — provided for API symmetry, documented as a copy.

Why: True zero-copy receive needs direct-placement RECV (posting the user MR as the recv SGE and bypassing reassembly), which conflicts with the credit/fragment ring built in #36. The spec allowed "或等价借还模型"; the send path captures the primary zero-copy win, and the doc is explicit about the recv copy.

Tradeoffs

Tradeoff Single-frame zero-copy vs. fragmented zero-copy

Alternatives: (a) reject buffers larger than one frame payload; (b) fragment a large Buffer across frames with multiple SGEs.

Pros/cons: (a) simple, correct, covers the common small-message zero-copy case; (b) supports arbitrarily large zero-copy sends but complicates SGE/credit accounting.

Chosen: (a) — a Buffer bigger than one frame returns ErrMessageTooLarge. Large payloads can use SendMsg (which fragments with a copy); fragmented zero-copy is a future enhancement.

Open Questions

Question Direct-placement zero-copy receive?

Assumption: Copy-on-recv is acceptable for v1; the send path is where zero-copy matters most for throughput.

Verify: If recv-side zero-copy is needed, design a separate "registered recv" mode that posts user MRs as recv SGEs and bypasses the reassembler (incompatible with credit fragmentation, so likely a distinct Conn mode).
