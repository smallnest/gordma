Implementation Notes

Issue #38 — rdmanet: Close 与资源回收 — 2026-06-13

Design Decisions

Decision Idempotent Close via sync.Once + atomic closed flag

Ambiguity: "Close 幂等；Close 后所有收发方法返回明确的 closed 错误".

Choice: Conn.Close runs its body in a sync.Once and sets an atomic.Bool. transport() checks the flag first and returns gordma.ErrClosed, so SendMsg/RecvMsg/Read/Write all fail fast after Close.

Rationale: Once+atomic is the idiomatic idempotent-close pattern and is race-free; the flag check centralizes the post-close error in one place.

Decision Graceful FIN control frame for peer-side io.EOF

Ambiguity: "对端关闭后本端 RecvMsg/Read 返回 io.EOF" — RDMA has no built-in stream FIN.

Choice: Added a flagFin control frame. shutdown best-effort sends FIN before tearing down; the receiver closes a peerFin channel, and nextMessage returns io.EOF once buffered frames drain (with a race-safe drain of any frame that arrived just before the FIN).

Rationale: A FIN frame is the cleanest way to translate "peer closed" into io.EOF, matching net.Conn expectations; it reuses the existing credit-slot control path.

Decision Close wakes blocked callers via the closed channel

Ambiguity: "Close 能唤醒阻塞中的 SendMsg/RecvMsg/Read/Write".

Choice: All blocking selects already include <-t.closed; close() closes that channel and the credit tracker, so acquire()/channel waits unblock and return closedErr().

Rationale: The transport was built channel-first in #35/#36 precisely so Close is a single broadcast.

Deviations

Deviation Release order is MR→QP→CQ→PD (→Context), not the issue's "QP→CQ→MR→PD"

Spec: Acceptance criterion lists "QP→CQ→MR→PD".

Implemented: MR is closed first, then QP→CQ→PD→Context.

Why: An MR must be deregistered before its PD is deallocated, and freeing the MR before the QP avoids any in-flight DMA into a region whose dealloc is pending. Closing MR first is the safe superset of the intent ("MR before PD"); the relative QP/CQ/MR order does not affect correctness as long as MR precedes PD. The rdma_cm path delegates to the root CMConn.Close which already orders QP→CQ→PD.

Tradeoffs

Tradeoff Best-effort FIN vs. guaranteed delivery

Alternatives: (a) fire-and-forget FIN then tear down; (b) wait for FIN's send completion before releasing resources.

Pros/cons: (a) Close returns promptly, but a FIN can be lost if the QP errors concurrently; (b) guarantees the peer sees EOF but can block Close indefinitely on a dead link.

Chosen: (a) — Close must not hang. If the FIN is lost the peer still observes a connection error on its next op; the FIN is an optimization for the clean-shutdown case.
