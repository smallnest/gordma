Implementation Notes

Issue #42 — rdmanet: UD 带外地址注册机制 — 2026-06-13

Design Decisions

Decision Line-delimited JSON over TCP, mirroring the handshake package

Ambiguity: "风格与 handshake 包一致，纯 Go" — protocol shape left open.

Choice: One JSON request object per line, one JSON response line: {"op":"register|lookup","name":..,"addr":..} → {"ok":..,"addr":..,"error":..}. The Addr is carried as its String() form and rebuilt with ResolveAddr.

Rationale: Matches handshake's wire style, trivially debuggable, and reuses the already-tested Addr round-trip as the serialization.

Decision In-memory map, last-writer-wins

Ambiguity: Persistence/uniqueness semantics weren't specified.

Choice: A mutex-guarded map[name]addrString; re-registering a name overwrites. No persistence (per the PRD non-goal).

Rationale: A name directory for a running cluster; overwrite supports endpoint restarts cleanly.

Deviations

Deviation None

Implementation followed the spec: NewRegistry server, PacketConn.Register, package-level LookupAddr, all pure Go and unit-tested without hardware. The registry remains optional — Addr.String()/ResolveAddr still work standalone.

Tradeoffs

Tradeoff One-shot connection per request vs. persistent client conn

Alternatives: (a) dial-request-response-close per register/lookup; (b) keep a long-lived client connection.

Pros/cons: (a) dead simple, stateless, no connection management; slightly more TCP setup cost. (b) lower per-op latency but adds reconnect/liveness handling.

Chosen: (a) — registration/lookup are rare bootstrap operations, so per-op connection cost is irrelevant and statelessness keeps the server trivial.

Open Questions

Question Registry liveness / unregister?

Assumption: Names persist until overwritten or the registry stops; no explicit unregister or TTL.

Verify: If stale entries become a problem, add an unregister op or a TTL/heartbeat; the protocol can carry a new op without breaking existing clients.
