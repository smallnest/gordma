Implementation Notes

Issue #33 — rdmanet: rdma_cm 方式 Dial/Listen — 2026-06-13

Design Decisions

Decision Wrap gordma.CMConn rather than reimplement rdma_cm

Ambiguity: "复用根包 rdma_cm 路径" — the Issue says reuse but not at what layer.

Choice: Conn holds a *gordma.CMConn; Dial/Listen delegate to gordma.Dial/gordma.Listen, and rdmanet only adds the net-style address tracking and option plumbing on top.

Rationale: The root wrapper already brings the QP to RTS and owns PD/CQ/QP lifecycle; re-deriving that would duplicate cgo code and violate FR-16 (no root-package changes).

Decision DialTimeout is the primitive; Dial delegates to it

Ambiguity: Issue lists both Dial and DialTimeout without specifying their relationship.

Choice: Dial calls DialTimeout(addr, DefaultDialTimeout, opts...); a non-positive timeout falls back to the default.

Rationale: Single code path for establishment; mirrors net.Dial/net.DialTimeout familiarity.

Deviations

Deviation LocalAddr/RemoteAddr are partially populated

Spec: "返回有意义的地址（IP:port 语义）".

Implemented: Dialed Conn records the dial target as RemoteAddr; accepted Conn records the listener bind address as LocalAddr. The opposite side is empty.

Why: The root gordma.CMConn does not expose the resolved peer/local sockaddr, and exposing it would require modifying the root package (forbidden by FR-16). The addresses we do have are meaningful IP:port values; the rest is left for a future root-package enhancement (see Open Questions).

Tradeoffs

Tradeoff WithHandshake returns not-implemented vs. silently using rdma_cm

Alternatives: (a) ignore WithHandshake for now and always use rdma_cm; (b) return errNotImplemented when WithHandshake is set.

Pros/cons: (a) "works" but silently does the wrong thing, hiding a missing feature; (b) explicit and safe, surfaces the gap until #34 lands.

Chosen: (b) — failing loudly on an unimplemented option is safer than a silent semantic mismatch.

Open Questions

Question Should the root package expose CMConn peer/local addresses?

Assumption: Full IP:port on both sides is not required for this Issue's acceptance.

Verify: If symmetric LocalAddr/RemoteAddr is desired, a small root-package addition (storing the resolved sockaddr on CMConn) would let rdmanet populate both — worth a follow-up Issue.

Question rdma_cm path only build-verified, not run

Assumption: conn_linux.go's rdma_cm delegation is correct; verified by stub cross-build and the negative Linux tests (which Skip when a device is present).

Verify: A real two-node RDMA run (or CI on an RDMA runner) is needed to confirm end-to-end establishment; covered conceptually by #44's bench tool.
